# Hermes Agent 0.2.31 Follow-up Fix Spec

## Baseline

- Target package: `hermes-agent-0.2.31-stream-routing-fixed.vsix`
- Source directory: `outputs/hermes-agent-vscode-extension`
- Package version at inspection time: `0.2.31`

This spec is for a scoped follow-up patch on top of the current stream-routing-fixed build. It must not introduce unrelated product, visual, or protocol changes.

## Goal

Fix the remaining interaction and rendering issues identified in the current version:

1. Session history rename still shows a check-confirm button.
2. Top title edit does not place the cursor at the clicked text position.
3. Document diff preview is not character-level and cannot visibly show added text in the editor.
4. Pasted files in the input box have no extension-side attachment lifecycle.
5. Hermes Agent document-column isolation is only partial.
6. User message bubbles do not use the VS Code theme accent tint.
7. `/skill` input does not reliably open the full list, filter live, or select an exact skill on Space.
8. Running agent status text should be bold.
9. Conversation content does not adapt when the VS Code column narrows.
10. Long Thinking content expands too much and hides the current workflow position.
11. File paths in action summaries should be clickable and open in the document editor column.

## Allowed Change Scope

Only these files may be changed:

- `media/main.js`
- `media/styles.css`
- `extension.js`

Do not change:

- `package.json`
- `package-lock.json`
- README, CHANGELOG, license, icon, or image resources
- ACP transport protocol code unless a currently listed requirement is impossible without it
- tests, except if a small focused assertion is requested later

## Non-goals

- Do not redesign the whole chat UI.
- Do not change ACP stream routing behavior.
- Do not change send/stop behavior.
- Do not change Mode semantics.
- Do not add model/effort settings work in this patch.
- Do not change ordinary text paste behavior.
- Do not modify documents during diff preview before user approval.

## Detailed Requirements

### 1. Session History Rename

Current problem:

- Rename mode still renders a `✓` confirm button.
- Clicking the button still acts as a confirmation action.

Required behavior:

- Enter rename mode from the edit icon.
- While renaming, do not show a check-confirm button.
- The rename input must keep focus while the user types.
- Save only on:
  - blur,
  - Enter,
  - clicking another session,
  - clicking outside the history popover.
- Escape cancels rename and restores the previous title.
- Do not post `renameSession` on every keystroke.

Implementation notes:

- In `renderHistory()`, remove the `renaming ? "✓" : icons.edit` rendering path.
- The edit button should only enter rename mode.
- Keep a local rename draft so global `postState()` does not recreate the input on each character.

Acceptance:

- Rename a session by typing multiple characters continuously; focus must not drop after the first character.
- No checkmark confirm button is visible in rename mode.
- Blur saves the new name.
- Escape cancels the edit.

### 2. Top Title Edit Cursor Placement

Current problem:

- Clicking the session title enters edit mode, but the input only receives focus.
- It does not place the cursor at the clicked text index.

Required behavior:

- Clicking a character in the title should enter edit mode and place the cursor at that character position.
- Never call `input.select()`.
- Use `setSelectionRange(index, index)` after render.
- If index calculation fails, place the cursor at the end, but never select all text.

Implementation notes:

- Capture the click `clientX` before `render()`.
- Estimate the text index from the rendered title text using a canvas text measurement or a temporary DOM measurement helper.
- After rendering `#titleInput`, call `focus()` and `setSelectionRange()`.

Acceptance:

- Clicking the middle of a title places the caret near that clicked position.
- The title is not auto-selected.

### 3. Document Diff Preview

Current problem:

- If `oldText` is found, the whole old range is decorated red.
- Added text is represented by a green range over existing text, not visible as the actual inserted text.
- Pure insertions create zero-length ranges and may not visibly show the new text.
- Confirmation diff display is line-list based and not in final document order.

Required behavior:

- Preview must be decoration-only and must not modify the document source before approval.
- Deleted/replaced old characters: red background + line-through.
- Added/replacement new characters: green background and visibly rendered text.
- Granularity should be character-level for changed continuous ranges, not entire paragraph unless the whole paragraph changed.
- Added text should appear at the actual insertion position using `TextEditorDecorationType.after.contentText` when the source document cannot contain it yet.
- Confirmation diff should show changes near their relevant location in final order, not as all removals first and all additions after.

Implementation notes:

- Replace the direct `removedRanges.push(oldText full range)` path with a small character diff helper.
- For replacement:
  - decorate deleted spans in the old document;
  - render new spans with `after.contentText` near the matching anchor.
- For pure insertion:
  - attach an `after` decoration at the insertion point with the inserted text.
- Keep `clearDocDiff()` responsible for disposing all decoration types and backup state.

Acceptance:

- Changing one word in a paragraph only marks that word/changed characters, not the whole paragraph.
- Adding a sentence displays that new sentence in green at the intended location without changing file text.
- Reject clears decorations and leaves the source file unchanged.
- Accept clears decorations and lets the existing permission flow continue.

### 4. Input Paste File Backend Lifecycle

Current problem:

- The webview sends `pastedFile`, but `extension.js` has no handler.
- The attachment may show with a fake path and cannot reliably be used as context.

Required behavior:

- Pasting a file while the input has focus creates a real attachment object with a usable `file://` URI.
- The file must be stored in an extension-controlled temporary attachment directory.
- The frontend should update attachment state only after receiving the extension-confirmed attachment.
- Text paste remains unchanged.
- After paste, input focus and caret position return to the prompt.

Implementation notes:

- Add an `onMessage` case for `pastedFile`.
- Decode `dataUrl`, write bytes to a temp directory under the extension/global storage path or OS temp path.
- Post a new message, e.g. `pastedFileReady`, with `toAttachment(uri, "file")`.
- In `main.js`, handle `pastedFileReady` like `localPicked`.

Acceptance:

- Paste a file into the prompt.
- The attachment row shows the file.
- Sending the prompt includes an attachment with real `uri` and `path`.

### 5. Document Column Isolation

Current problem:

- Extension-triggered opens use `findDocumentColumn()`.
- User-triggered VS Code file opens can still land in the agent/webview column.

Required behavior:

- No text document should remain opened in a Hermes Agent webview column.
- If a text editor appears in an agent column, move it to a document editor column.
- This must not affect Hermes Agent editor-session panels or sidebar behavior.

Implementation notes:

- Track agent columns from Hermes-owned panels plus tab groups containing Hermes webviews where possible.
- Add a guarded listener around active editor or tab group changes.
- If active text editor is in an agent column, call `showTextDocument(editor.document, { viewColumn: findDocumentColumn(), preview: false })`.
- Use a reentry guard to avoid loops.

Acceptance:

- With focus in the Hermes Agent column, opening a file from VS Code Explorer moves or opens the file in a document editor column.
- Hermes Agent panels still open in their intended column.

### 6. User Message Bubble Accent Tint

Current problem:

- User-sent message bubbles use generic gray/white and are hard to distinguish from agent output.

Required behavior:

- Only user message bubbles should use a VS Code theme accent-tinted background.
- The tint should be transparent/subtle, not a solid accent fill.
- Text readability must remain controlled by VS Code foreground tokens.

Implementation notes:

- In `styles.css`, adjust `.message.user .bubble`.
- Use `color-mix(in srgb, var(--vscode-accent) 14%, var(--bg))` or similar.
- Do not change assistant answer styling.

Acceptance:

- User bubbles are visually distinct from assistant content in both light and dark themes.
- No fixed product color is introduced.

### 7. `/skill` Input Interaction

Current problem:

- Typing `/` may not show the full skill list.
- Typing a skill name may not filter live.
- Typing a full skill name followed by Space may not select the skill.

Required behavior:

- When prompt starts with `/`, open the full skill list immediately.
- While typing after `/`, filter by skill name and, secondarily, description.
- Do not full-render the webview on every input; preserve typing focus.
- Space selects only when there is an exact skill-name match.
- If no exact match exists, do not swallow the Space key.
- Clicking a skill also selects it and returns focus to the prompt.

Implementation notes:

- Ensure the popover exists before calling `renderSkillListOnly()`. If opening from closed state, do one controlled render, then subsequent typing uses list-only update.
- Track `_skillFilter`.
- Exact match should compare lowercased names without the leading slash.

Acceptance:

- Type `/`: full list appears.
- Type letters continuously: list filters without focus loss.
- Type a full skill name and press Space: selected skill chip appears and `/skillName` is removed from input.

### 8. Agent Running Status Bold

Current problem:

- Running status text at the bottom of the assistant answer is not bold enough.

Required behavior:

- `Working...` status line should be bold while running.
- `Interrupted` and `Tool Interrupted` remain muted italic.

Implementation notes:

- Only change `.working-status.working` font weight.

Acceptance:

- During a running response, the animated `Working...` text is visibly bold.

### 9. Conversation Responsive Width

Current problem:

- Output generated in a wide window can remain too wide after the window narrows, requiring horizontal scrolling.

Required behavior:

- Conversation content adapts to the current webview width.
- Normal prose, tables, attachments, user bubbles, thinking rows, and action summaries must not force horizontal page scrolling.
- Code blocks may scroll internally but must not widen the whole conversation.
- The layout should respect VS Code editor-column practical minimum width; below that, preserve controls rather than causing full-page horizontal overflow.

Implementation notes:

- Add or tighten `min-width: 0`, `max-width: 100%`, `overflow-wrap: anywhere`, `word-break: break-word` on:
  - `.thread`
  - `.assistant`
  - `.answer`
  - `.thinking`
  - `.timeline-body`
  - `.step-summary`
  - `.bubble`
  - `.question-text`
  - `.table-wrap`
  - `.code-sample`
- Keep code/pre blocks internally scrollable.

Acceptance:

- Generate long content at wide width, narrow the VS Code column, and verify prose reflows without horizontal page scrolling.
- Long paths or long words wrap or stay inside internal scroll containers.

### 10. Long Thinking Content Max Height

Current problem:

- Long Thinking content fully expands and makes users lose the current workflow position.

Required behavior:

- Expanded Thinking text should show at most about 10 lines.
- Overflow should scroll within the Thinking item.
- Action detail blocks keep their existing max-height behavior.

Implementation notes:

- Apply a max-height to `.step-content p` for thinking items or add a class for thinking text content.
- Use line-height based sizing, e.g. `max-height: calc(1.55em * 10)`.
- Preserve manual expand/collapse behavior.

Acceptance:

- A long Thinking block does not consume the entire Working area.
- The user can scroll inside the Thinking block to inspect more text.

### 11. Clickable File Paths In Action Summaries

Current problem:

- Read/Edit/Write/Open action summaries contain paths as plain text.

Required behavior:

- Local absolute paths, workspace-relative paths, and `file://` URIs in action summaries should render as clickable links.
- Clicking opens the file in the document editor column via the existing document-column routing.
- Do not turn arbitrary non-path text into links.

Implementation notes:

- In `renderThinkingStep()`, when rendering action `description`, pass it through a local path-link renderer instead of plain `h(description)`.
- Link should use `data-path` or `data-uri`.
- Reuse existing delegated click handling for `a[data-path]` where possible.
- Extension side should route through `openAttachment()` / `findDocumentColumn()`.

Acceptance:

- A `Read /path/to/file.js` action shows the path as a highlighted clickable link.
- Clicking it opens the file in a document editor column.

## Verification Plan

Run after implementation:

```bash
npm run lint
npm run test:unit
```

Then manually verify in VS Code:

1. Session history rename continuous input, blur save, Escape cancel, no checkmark.
2. Top title click enters edit with caret near clicked location and no full selection.
3. `/` opens all skills; typing filters; exact name + Space selects.
4. Paste file into prompt and send; attachment has a real URI.
5. User file open from Explorer while Hermes Agent column is focused opens in document column.
6. Diff preview shows character-level red/green decorations without source mutation before approval.
7. Long Thinking content is capped around 10 lines.
8. Narrowing the VS Code column does not produce page-level horizontal scroll.
9. Action path links open files in document column.

If existing smoke tests still terminate with `SIGABRT`, record it separately and do not claim full smoke verification.

## Risk Controls

- Keep changes local and mechanical where possible.
- Avoid broad refactors of render/bind lifecycle.
- Do not change message persistence format except adding optional attachment fields already used by existing attachment objects.
- Use guards for editor-column migration to avoid focus loops.
- Dispose all new decoration types in `clearDocDiff()`.
- Keep frontend state updates minimal during typing to avoid focus loss.
