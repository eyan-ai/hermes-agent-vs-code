- Status: confirmed
- Prerequisites: [00-spec-index.md](./00-spec-index.md)
- Evidence: 用户复测反馈、已确认 HTML 原型、`0.2.44` 当前源码
- Confirmed decisions: D-01 至 D-19
- Blocking open questions: 无

## 背景

当前 Hermes Agent 插件已经具备 ACP 权限请求、只读 Diff 预览、无限等待确认、文档 Editor 路由和 Working 工具过程展示。但现有确认模型主要面向一次局部 Edit：用户看到一个问题和固定按钮，然后选择允许或拒绝。

当修改扩大到整篇重构时，该模型暴露出三个问题：

1. 用户只能看到局部 Patch，缺少对最终全文结构和完整结果的判断依据。
2. 候选稿完成后仍需要用户主动寻找结果入口，不符合“系统请求审批时主动摆出审批内容”的预期。
3. 用户除了 Allow/Deny，还经常需要表达“不要这样改，改成另一种方式”，现有权限响应不能承载自由意见。

同时，Working 动作中的路径和网址存在视觉高亮割裂；代码类 Action 可能把原始代码直接塞进标题行，导致过程难以扫描；任务中 Agent 提问与用户回答也没有形成稳定、可追溯的过程记录。

## 受影响用户与任务

- 在 VS Code 内使用 Hermes 修改文档、代码和项目材料的用户。
- 需要审阅整篇重构、跨章节调整或大量内容重写的用户。
- 在权限确认时需要提供替代要求，而不是简单允许或拒绝的用户。
- 需要从 Working 快速打开本地文档或外部参考链接的用户。

## 当前待修改内容汇总

### S-01 插件侧审阅分级与 Diff

- 新增文件：完整展示待创建内容，不构造无意义的红绿 Diff。
- 局部修改：沿用文档 Editor Diff 或确认区域紧凑 Diff。
- 完整候选稿：目标文档未打开且实际变化量达到审阅阈值时，进入独立 Result/Changes Review；文档已打开时仍使用原文档内联 Diff。
- 分类发生在实际 ACP 写入审批点，只决定插件 UI，不要求 Agent 提供“大修改”语义标签。
- Diff 只高亮实际变化行，删除整行红色、增加整行绿色，不使用删除线。

### S-02 完整候选稿 Review 流程

- 插件收到未打开文档的大范围写入审批后，在 Agent 右侧自动拉起独立临时 Review Editor。
- Review 默认显示 Result，可切换 Changes，原文在允许前保持不变。
- 用户允许后仍由 Agent 执行原写入；插件不自行覆盖文件。
- 用户拒绝则清理 Review；用户输入替代意见则拒绝当前候选并反馈给同一 Agent。
- 同一路径的下一版候选复用原 Review Editor。

### S-03 通用确认与自由输入

- 复用现有确认弹窗容器、位置和样式。
- 预设选项点击即提交。
- 自由输入按 Enter 提交，Shift+Enter 换行。
- 自由输入适用于 Edit、Execute、Review、一般 Clarify 等需要用户意见的场景。
- 自由输入不得误判为允许当前操作。

### S-04 Working 动作和问答记录

- Read/Edit 等本地动作显示文件名而非完整路径。
- 完整路径仅作为 tooltip 和点击依据。
- 外部网址和本地路径都使用普通正文颜色，仅在悬停时出现完整、连续下划线。
- 运行代码的 Action 标题使用“动作类型 + 自然语言目的”，不直接展示脚本或命令正文。
- 脚本、命令和必要结果放在现有展开详情中；只有确有输入输出关系时才使用 `IN/OUT`，不把它作为所有代码 Action 的固定模板。
- Agent 中途问题和用户回答作为 Working 时间线事件持久展示。

### S-05 Run Settings Model

- 保持现有 Mode 选择和语义不变。
- Model 使用上下布局：标题独占一行，下拉框在下一行占满可用宽度。
- 不显示 Reset 按钮。
- 可选模型来自 Hermes/ACP 当前系统真实配置，不维护插件硬编码模型名单。
- 当前选择保存到会话和全局“上次选择”，新会话自动继承。
- 继承值失效时回退到 Hermes 当前默认模型。

## 目标

- G-01：让修改审阅方式与修改规模匹配，避免用局部 Patch 审批整篇重构。
- G-02：当系统进入待审批状态时，主动展示需要审批的完整内容。
- G-03：支持用户在确认点直接给出替代意见，并安全地重新生成方案或操作。
- G-04：保持原文在最终确认前不变，所有应用操作可明确放弃和恢复。
- G-05：让 Working 成为可扫描、可点击、可追溯的过程记录。
- G-06：所有新能力遵循当前 Hermes UI 规范，不以局部功能为由重做确认弹窗和会话布局。
- G-07：让 Model 选择真实可用、可跨新会话延续，同时不改变 Mode 的既有交互。

## 成功标准

- 用户面对完整候选稿时，不需要离开自动拉起的审阅工作区即可查看全文结果和完整变化。
- 用户在任何支持意见的确认点，都能直接点击选项或输入替代要求，不需要额外“继续”操作。
- 自由意见不会执行原待确认操作，也不会造成重复提交。
- 插件在明确允许前不写入原文；允许后由 Agent 按原 ACP 流程执行写入。
- Working 中的文档、网址、代码执行详情和问答可正确打开、查看和追溯；折叠状态下可以通过自然语言标题快速理解动作目的。
- 新组件在多种 VS Code Color Theme 和最小 Editor 宽度下保持现有 UI 一致性与可用性。

## 强制约束

- C-01：复用 `.permission-panel` 所在的现有弹窗/确认区域框架和布局位置。
- C-02：复用现有主题 token、边框、字号、圆角、间距、hover、focus 和 disabled 规范。
- C-03：不得引入第二套 Confirmation Modal、悬浮位置或独立视觉语言。
- C-04：不得破坏已经修复的会话自适应、多附件单行横向滚动、长用户消息展开收起、输入焦点、队列、Todo、Thinking、历史搜索和停止状态。
- C-05：所有待确认请求继续按 `sessionId + requestId` 隔离，防止跨会话和迟到响应。
- C-06：不自动超时 Allow 或 Deny；提醒仅提示，不改变状态。

## 非目标

- 不重做 Hermes 整体视觉设计。
- 不修改 CLI、模型、Personality、Mode 或 Skill 行为。
- 不在本轮设计协同多人批注、Plan 审批、版本树或复杂评论管理。
- 不改变系统密码、Secret、OAuth、操作系统权限等专用安全输入组件。
- 不将所有普通消息都包装成确认组件。
- 不修改 Agent 的 Plan 或自动模式语义，也不保证将多个局部 Permission 合并成整篇候选。
